# McpGo Playwright — второй этап качества и производительности (19.11.2026)

## Что реализовано в исходниках

1. **Профилирование горячего пути:** `restricted-proxy.mjs` сохраняет 500 последних значений длительности и размера ответа по типу upstream-вызова (включая `upstream:tabs:list`, действие, создание snapshot). `/healthz` показывает p50/p95 и размер ответа, без HTML, URLs, снимков, заголовков и токенов. Повторное чтение уже проверенной таблицы вкладок внутри одного `mcpgo_tab_action(select/close)` убрано: владелец и индекс по-прежнему проверяются в сериализованном браузерном запросе. За пределами *этого одного запроса* кеширование таблицы вкладок запрещено.
2. **Snapshot A/B:** `MCPGO_BROWSER_SNAPSHOT_MODE=full|none` и независимый `MCPGO_AUTOSEND_SNAPSHOT_MODE=full|none`; допустимы только перечисленные режимы. Базовый режим остался `full`, пока надёжность `none` на реальных SPA не подтверждена. `mcpgo_inspect_page` продолжает явно предоставлять snapshot, короткий `find`, `recover` и `verify` при `none`.
3. **Браузерные read-only проверки:** `mcpgo_inspect_page(strategy=state)` проверяет точное URL, CSS-состояние `visible/hidden/attached/detached`, текст элемента, same-origin iframe, *факт наблюдения завершённой загрузки ресурса* по URL path (не HTTP-успех). `strategy=scroll` прокручивает только текущий документ или явно указанный контейнер (не более 12 шагов, 80–1000 px, общий ограниченный таймаут). `strategy=recover` перечитывает свежую accessibility-ссылку через `browser_find`, **не** повторяет клик. Все страницы проверяются только под прежним McpGo `workspace_id`, очередью и ownership guard. В `browser_evaluate` передаётся строго фиксированная функция с JSON-кодированными параметрами; произвольный код пользователя не принимается.
4. **Нестандартные документы:** `strategy=visual, screenshotOnly=true` сразу запрашивает WebP CSS-scale screenshot без попытки прочитать accessibility tree у SVG/no-body страниц. Обычный visual по-прежнему соединяет accessibility + screenshot, но только по явному запросу.
5. **Профили MCP-инструментов:** `MCPGO_BROWSER_TOOL_PROFILE=full|core|vision|diagnostics`. `full` — обратная совместимость; `core` — только типичные инструменты навигации/действий, inspect и таб-изоляции; `vision` добавляет визуальные инструменты; `diagnostics` дополнительно открывает отладочные инструменты. Фильтрация меняет **каталог**, а не выдаёт дополнительные права и не отменяет ownership checks. Переключение применяется только после перезапуска proxy; ChatGPT может кешировать старый каталог. Даже в `core` управляемые операции inspection используют строго фиксированные внутренние browser функции.
6. В манифестах macOS dev/runtime и Windows добавлены новые `inspection-conditions.mjs` и `tool-profiles.mjs`; CI проверяет их синтаксис.

## Измерения на изолированном настоящем Chrome

Профиль временный, безопасный loopback QA-сайт, без личного Chrome Extension. Все проверки прошли. Небольшие тесты зависят от системной нагрузки: не используйте их как SLA или заявление о том, что `none` всегда быстрее.

| Сценарий | full | none |
|---|---:|---:|
| Один клиент, 4 последовательных клика, медиана | 307,8 мс | 300,8 мс |
| Один клиент, ответ клика (медиана, UTF-8) | 844 байта | 603 байта |
| Три **параллельно** работающих клиента, по 5 кликов: медиана вызова | 629,5 мс | 1116,6 мс |
| Те же три клиента: p95 вызова | 1011,7 мс | 2218,9 мс |
| Три клиента: ответ клика (медиана, UTF-8) | 946 байт | 603 байта |
| Три клиента: `browser_tabs:list` | 141 | 141 |

Разные прогоны выполнялись последовательно и скорость существенно менялась от текущего состояния Chrome/ОС. В `none` действительно меньше данных в ответах, но гарантированного ускорения *времени действия* нет. Объём в байтах — не число токенов GPT: точное число токенов без конкретного токенизатора/модели не измерялось.

В одном успешном конкурентном прогоне (три клиента) `stage_tab_verification` имел медиану **25 мс**, p95 **223 мс**, а upstream `browser_click` медиану **321 мс**: значительная часть общей задержки вызова уходила на сериализованные проверки/переключение активной вкладки. В другом прогоне p95 tab-verification составлял только 9 мс. Это показатель изменчивости нагрузки, а не доказательство проблемы с одной конкретной функцией.

## Регрессии и безопасность

- Три клиента посылали клики **конкурентно**; каждый прочёл собственный увеличенный счётчик, все 15 кликов подтверждены, чужая вкладка не использована.
- Реальный Chrome подтверждает `state` (точный URL, same-origin iframe, завершённый ресурс), виртуализированный скролл, восстановление ссылки через find, WebP fallback для отдельного SVG-документа без HTML body.
- `core` проверен на настоящем изолированном Chrome: каталог с 50 до **21** видимого инструмента, обязательные workspace/tab/inspect на месте. Установка расширения пользователя и его версии не менялись.
- Стандартные Node regression tests: **160 PASS, 2 SKIP, 0 FAIL**; AutoSend **122/122**; Terminal **42/42**; Python **83 + 65 + 16** PASS (164/164).
- Не отключали URL/ownership-проверки, не ввели автоматические повторы mutating calls, не включали пользовательские network/console/trace дампы, не брали credentials или реальные страницы в QA.

## Неизменённые ограничения

- `--snapshot-mode=none` остаётся opt-in, а profile `full` — default, поскольку при трёх клиентах p95 зависит от системной нагрузки и ни один короткий A/B не доказывает безопасное отключение snapshots во всех UI.
- Нет подтверждения чтения cross-origin iframe через `document.contentDocument`: они недоступны из JS по same-origin policy, требуется Playwright locator/визуальный обход в отдельном исследовании.
- Режим `screenshotOnly` для SVG требует явного выбора; автоматического распознавания таких страниц пока нет, так как нельзя допустить, чтобы зависающий `browser_snapshot` блокировал общую очередь.
- Сохранена архитектурная граница: AutoSend использует отдельный Playwright backend, но dev-установка McpGo на данном Mac разделяет writable runtime с уже подключёнными клиентами. Любой реальный dev sync затрагивает эти браузерные службы. Внешний app release, push и prod — отдельно.

## Дополнительное исправление после нагрузочного dev-теста: зависающие метаданные вкладок

В текущем dev наблюдался `upstream:tabs:list` **68 504 мс**, после чего общий прокси правильно включал fail-closed `BROWSER_ACTION_OUTCOME_UNKNOWN / quarantined`. Это объясняет часть высоких p95 при большом числе/сложном состоянии вкладок. Точный вклад каждого личного Chrome tab без сбора приватных заголовков не измерялся.

Причина вероятного усиления задержек — существовавший в `playwright/patch-playwright.mjs` per-tab timeout **2500 мс** на необязательный `page.title()` и **1200 мс** на счётчики консоли. При последовательном обходе множества неотвечающих вкладок сумма может выходить за общий бюджет. Новый патч оставляет `headerSnapshot` и нативные группы вкладок без изменений, но ограничивает необязательные поля **250 мс** и **100 мс** на каждую вкладку. Стабильные URL/tab handles и проверки ownership от этих полей не зависят; на медленных страницах вместо заголовка/счётчиков могут отображаться пустые метаданные.

- Проверка `patchSource()` идемпотентна, корректно мигрирует с предыдущего 2500/1200-патча и **отказывается менять неизвестную upstream-сигнатуру**.
- Регрессионный сценарий с восьмью зависшими заголовками проходит приблизительно за **2,0 секунды**, а не занимает по 2,5 секунды на вкладку.
- После `npm ci` новый патч применяется автоматически и тесты проходят.
- Новые исходники и патч встроены в подписанный `McpGo Dev.app` RuntimeSeed. В уже работающем dev Runtime 0.0.86 установленные зависимости обновлены **только после остановки** Browser/Proxy/AutoSend Browser; сохранён резервный исходный bundle `release/dev/playwright-metadata-rollback-20261119/`. `Application Support/McpGo/Runtime` общий для установленного клиента и Dev — отдельный релиз не менялся.
- На **установленном расширении Chrome** после этого один холодный `browser_tabs:list` занял **4286 мс**, затем четыре последовательных read-only вызова — **1054, 117, 29, 47 мс**. Очередь осталась в `quarantined=false`, браузер `connected`. Ни одна пользовательская вкладка не закрывалась, и URL/названия не выводились в отчёты.
- Нельзя гарантировать отсутствие будущих зависаний от внешней нагрузки на Chrome; mutating calls с неизвестным исходом по-прежнему **не** повторяются автоматически. Проверить результат незавершённого действия на сайте следует до нового запроса.
